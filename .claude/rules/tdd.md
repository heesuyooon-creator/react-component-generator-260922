# TDD Rule

> **이 규칙은 Rigid다.** 상황에 맞게 변형하지 마라. 예외를 만들고 싶다는 판단이 들면, 그 판단 자체를 의심하라.

## 0. 우선순위

이 파일은 **기본값(fallback)**이다. 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그쪽이 우선**한다. 충돌 시 이 파일의 내용은 무시한다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (계산, 상태 전이, 도메인 규칙)
- **API 엔드포인트/핸들러** (요청→응답 계약)
- **유틸리티 함수** (순수 함수, 데이터 변환)
- **버그 수정** (재현하는 실패 테스트 먼저)

### TDD가 불필요한 대상

- **타입 정의** (인터페이스, 타입 선언만 있는 파일)
- **설정 파일** (config, 빌드 스크립트, 환경변수 파일)
- **순수 UI** (마크업/스타일만 있고 로직이 없는 프레젠테이션 컴포넌트)
- **SQL** (마이그레이션, 스키마 정의)

판단이 애매하면: **로직이 있으면 적용, 없으면 생략**.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 몰아넣지 마라.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않고 넘어가는 것은 RED가 아니다.
- 실패 이유는 반드시 **"기능 미구현"**이어야 한다. 문법 오류, import 누락, 타입 오류로 인한 실패는 RED가 아니라 버그다 — 먼저 고치고 다시 실패를 확인하라.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 지금 요구되지 않는 기능을 미리 만들지 마라.
- **신규 테스트와 기존 테스트 모두 통과**를 확인한 뒤에만 GREEN으로 인정한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출을 수행한다.
- 리팩터링 전체 과정에서 **테스트는 계속 green이어야 한다.**
- 이 단계에서 **새로운 동작을 추가하지 마라.** 새 동작이 필요하면 다음 사이클의 RED로 넘겨라.

### 반복

REFACTOR가 끝나면 **다음 동작에 대한 RED로 돌아간다.** 사이클은 구현할 동작이 남아있는 한 계속된다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 사실을 발견하면, **그 코드를 삭제**하고 RED부터 다시 시작한다.
- **"참고용으로 남겨두기"도 금지.** 주석 처리, 별도 파일 보관, `// TODO: 나중에 테스트` 표시 등 어떤 형태로도 남기지 마라.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 비용이 낮다. 낮은 비용을 이유로 생략하는 것은 모순이다. 단순함은 테스트 생략의 근거가 아니라 테스트가 쉽다는 근거다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 코드가 GREEN에 도달하는 순간 테스트를 미룰 동기는 사라진다. 지금 없으면 영원히 없다. |
| "시간이 없다" | 테스트 없이 짠 코드는 디버깅 시간으로 그 차이를 반드시 되갚는다. 지금 아끼는 시간은 나중에 이자를 붙여 지불하는 시간이다. |
| "삭제하면 낭비" | 매몰비용이다. 순서를 어긴 코드를 유지하는 것은 규율을 무너뜨리는 대가를 치르는 것이며, 그 대가가 코드 몇 줄보다 크다. |
| "프로토타입이다" | 프로토타입은 살아남아 프로덕션이 된다. "프로토타입이니까"는 예외가 아니라 나중에 발견될 부채의 예고다. |

## 5. 요약

**테스트 없이 작성된 프로덕션 코드는 존재해서는 안 된다.** 발견하면 삭제하고 RED부터 다시 시작하라.
