# commit: 변경사항 분석 후 컨벤션 커밋

현재 저장소의 변경사항을 분석해 논리적 단위로 나누고, 각 단위에 맞는 한국어 커밋 메시지를 작성해 바로 커밋한다. 사용자 승인 절차 없이 자동으로 진행한다.

## 절차

### Step 1: 변경사항 분석

- `git status`로 전체 변경 파일(staged/unstaged/untracked)을 확인한다.
- `git diff`와 `git diff --staged`로 실제 변경 내용을 읽는다. 파일명만 보고 추측하지 않는다.
- `git log --oneline -10`으로 이 저장소의 기존 커밋 메시지 스타일이 있으면 참고한다. 히스토리가 없으면 아래 기본 컨벤션을 따른다.
- 민감 정보(.env, credentials, 키 파일 등)가 포함되어 있는지 확인하고, 있다면 사용자에게 경고하고 해당 파일은 제외를 제안한다.

### Step 2: 논리적 단위로 분류

- 서로 관련 없는 변경(예: 기능 추가 + 무관한 리팩터링)은 별도 커밋으로 분리한다.
- 하나의 목적으로 묶이는 변경(같은 기능/버그 수정에 걸친 여러 파일)은 하나의 커밋으로 묶는다.
- 스코프가 애매하면 diff 내용을 근거로 스스로 판단해 분리 여부를 정한다. 확인 질문 없이 진행한다.

### Step 3: 커밋 메시지 작성

- 형식: `<type>: <한국어 요약>`
  - `feat`: 새로운 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 코드 구조 변경
  - `chore`: 빌드/설정/의존성 등 잡무성 변경
  - 위 네 가지로 분류되지 않으면 `docs`, `test`, `style` 등 널리 쓰이는 타입을 추가로 사용할 수 있다.
- 요약은 "무엇을 왜" 관점으로 간결하게 작성한다. diff에서 확인되지 않는 내용은 지어내지 않는다.
- 본문(body)이 필요할 만큼 변경이 크면 요약 뒤 빈 줄을 두고 불릿으로 핵심 변경을 나열한다.
- 커밋 메시지 끝에는 대화의 system-reminder에 지정된 attribution 라인이 있으면 그대로 포함한다.

### Step 4: 바로 커밋

- 승인을 구하지 않고 관련 파일만 `git add`로 스테이징한 뒤(`git add -A`/`git add .` 금지) 커밋을 생성한다.
- 여러 개의 논리적 단위로 나누었다면 각각 별도 커밋으로 순서대로 진행한다.
- 커밋 후 `git status`/`git log --oneline -n`으로 정상 반영되었는지 확인한다.
- 진행 후 어떤 파일들을 어떤 메시지로 커밋했는지 사용자에게 간단히 결과를 보고한다.

## 금지 사항

- `git commit --amend`, `--no-verify`, `--no-gpg-sign` 등은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- pre-commit 훅 실패 시 원인을 고치고 새 커밋을 만든다. 훅을 우회하지 않는다.
- 민감 정보(.env, credentials, 키 파일 등)가 포함된 파일은 승인 없이도 절대 커밋하지 않는다. 발견 시 해당 파일만 제외하고 커밋한 뒤 사용자에게 경고한다.
